3. Unity Catalog: what it is and how it works

What it is: Databricks' unified governance layer for data and AI assets across workspaces. It's the central place to manage who can see and use tables, views, volumes, models, and files, and it records lineage and audit logs.

The three-level namespace: catalog.schema.table. A catalog holds schemas, a schema holds tables/views/volumes/models.

How it works (core pieces): - Metastore: one per region, attached to one or more workspaces. It holds the metadata and the permission grants. - Catalogs and schemas: organize data by domain or environment (for example dev, prod, or by business area). - Privileges: GRANT SELECT, MODIFY, USE CATALOG, USE SCHEMA, CREATE TABLE ... to users, groups, or service principals. Groups are managed centrally (for example through SCIM or Entra ID sync). - Storage credentials and external locations: how Unity Catalog reaches cloud storage (for example ADLS Gen2) without giving users direct storage keys. - Managed vs external tables: managed tables are stored in a UC-controlled location; external tables point to a path you own. - Lineage and audit: column- and table-level lineage, and audit logs of access. - Volumes: governed storage for non-tabular files. - Delta Sharing: share governed data with other organizations or platforms.

Why it matters for this role: It's the answer to "how do multiple workspaces share governed data safely," which is exactly the multi-tenant problem you solve on the platform side.

A. Databricks fundamentals (Q1–Q15)

Q1. What is Azure Databricks? A managed Apache Spark-based analytics and AI platform on Azure, with notebooks, jobs, clusters, Delta Lake, and Unity Catalog for governance.

Q2. What is the difference between the control plane and the data plane? The control plane (Databricks-managed) handles the UI, notebooks metadata, and job scheduling. The data plane runs in your Azure subscription: clusters, storage, and networking. In a VNet-injected workspace, the clusters run in your VNet.

Q3. What is a cluster in Databricks? A set of VMs running Spark. Types: all-purpose clusters (interactive) and job clusters (created per job, terminated after). Job clusters are cheaper for scheduled work.

Q4. What are compute pools? Pre-warmed pools of idle VM instances that clusters can draw from, so start-up time drops. You pay for idle instances, so size and idle timeout matter for cost.

Q5. How do you control cost on Databricks? Auto-termination, job clusters over all-purpose clusters, cluster policies that cap node types and sizes, spot instances where tolerable, pools with sensible idle limits, and monitoring DBU spend per workspace or team.

Q6. What are cluster policies? Rules that restrict what users can create: allowed node types, max workers, mandatory tags, auto-termination. They enforce standards and cost control.

Q7. How do you manage user and group access in a Databricks workspace? Groups synced from Entra ID (SCIM), permissions granted to groups not individuals, and workspace-level entitlements (for example "allow cluster creation") separated from data permissions.

Q8. What is Delta Lake? An open table format on Parquet with a transaction log. It provides ACID transactions, schema enforcement, time travel, and efficient upserts (MERGE).

Q9. What is time travel in Delta? Querying earlier versions of a table by version or timestamp, using the transaction log. Retention is governed by table properties and VACUUM.

Q10. What does VACUUM do? Removes data files no longer referenced by the transaction log and older than the retention threshold. Lowering retention below the default has consequences for time travel and concurrent readers.

Q11. What is OPTIMIZE and Z-ORDER? OPTIMIZE compacts small files. Z-ORDER co-locates related data to speed up selective queries on the chosen columns.

Q12. What are Databricks Jobs and how do you run them? Scheduled or triggered workflows of notebooks, Python scripts, JARs, or SQL tasks, with dependencies, retries, and alerts. They can run on job clusters or serverless compute, depending on availability.

Q13. How do you deploy notebooks and jobs across environments? Source-controlled code in Git, promoted through pipelines, with environment-specific configuration. For jobs, use bundles (see Q18–Q20) or API/Terraform-based definitions.

Q14. How do you secure secrets used in Databricks notebooks? Use secret scopes backed by Azure Key Vault. Never hard-code secrets in notebooks. Reference them with dbutils.secrets.get.

Q15. How do you connect Databricks to ADLS Gen2 securely? Prefer Unity Catalog external locations and storage credentials (managed identity or access connector) over account keys. For legacy setups, use service principals with the least-privilege role on the storage container.

B. Databricks networking, security and operations (Q16–Q30)

Q16. What is VNet injection? Deploying the Databricks data plane into your own VNet, with public and private subnets. It gives you control of NSGs, routing, and private connectivity.

Q17. Why use Secure Cluster Connectivity (no public IP)? Clusters have no public IPs and connect outbound only to the control plane via relay, reducing exposure. It's a common banking requirement.

Q18. What are Databricks Asset Bundles (DABs)? A way to define jobs, pipelines, and related resources as YAML code, version them in Git, and deploy them to targets (dev, test, prod) with the Databricks CLI. The JD names this specifically.

Q19. How would you set up a CI/CD pipeline for a bundle? Validate the bundle (databricks bundle validate), run unit tests and lint, deploy to a dev target from feature branches, promote to prod via approval, and use per-environment variables and service principals for the deploy identity.

Q20. What's the difference between a bundle target and a workspace? A target is a deployment configuration (workspace host, variables, mode such as development or production). The same bundle can deploy to several targets.

Q21. How do you monitor Databricks jobs? Job run history, alerts on failure or duration, cluster and driver logs, and forwarding diagnostic logs to Azure Monitor or Log Analytics for KQL queries and dashboards.

Q22. How do you troubleshoot a slow Spark job? Check the Spark UI for skew, spill, shuffle size, and idle stages. Then look at file sizes (small-file problem), partitioning, broadcast joins, and whether the cluster is undersized or oversized.

Q23. What is data skew and how do you fix it? Uneven key distribution means a few tasks do most of the work. Fixes: salting keys, adaptive query execution (AQE), repartitioning on better keys, or broadcasting the small side of the join.

Q24. What is Photon? A vectorized query engine in Databricks, faster for SQL and DataFrame workloads. It's enabled per cluster and can affect cost.

Q25. What is autoscaling and when is it a problem? Clusters add and remove workers based on load. It's helpful for variable workloads, but it can hurt predictable cost and cause start delays if pools are not used.

Q26. How do you handle a Databricks workspace outage or a failed cluster start? Check the cluster event log, quota limits in the subscription, VNet and NSG rules, and DNS. Then check whether a recent policy or network change caused it. Communicate status through the incident process.

Q27. What are the quotas you watch for Databricks on Azure? vCPU quotas per region and VM family, public IP limits in the VNet design, and workspace-level limits on concurrent jobs and clusters.

Q28. How do you upgrade or migrate Databricks runtimes? Test the job in a dev workspace on the new runtime, check library and Spark-version changes, plan a staged rollout by team, and keep a rollback path.

Q29. How do you handle library management? Prefer cluster-scoped or workspace-scoped libraries from a controlled artifact feed. Pin versions, and avoid installing unvetted packages on shared clusters.

Q30. How do you isolate teams on a shared Databricks platform? Separate workspaces or catalogs per team or environment, group-based permissions, cluster policies per team, cost tags, and quotas. You can describe the isolation model you run on the 18-application platform.

Q36. What is a Databricks SQL warehouse? Compute optimized for SQL and BI workloads. Serverless or classic options exist. Size and auto-stop control cost.

D. Unity Catalog (Q41–Q55)

Q41. What is Unity Catalog? Databricks' central governance layer for data and AI assets across workspaces: access control, auditing, lineage, and discovery.

Q47. How does lineage work in Unity Catalog? UC captures table and column lineage from queries and pipelines, visible in the catalog explorer. It helps impact analysis and audit.

Q48. How do you share data across organizations with UC? Delta Sharing: a provider creates a share, a recipient consumes it, with governance kept on the provider side.

Q49. What are Volumes in UC? Governed storage for files (CSV, images, models, unstructured data) with the same permission model as tables.

Q52. How does UC help with compliance in banking? Central access control, audit logs of data access, lineage for data origin, and separation of duties through group-based grants.

Q53. What's the difference between workspace-level and account-level UC configuration? Account-level handles metastores, identity sync, and cross-workspace governance. Workspace-level covers compute and workspace-specific settings. Be accurate about which level you administer.

E. AKS and Kubernetes (Q56–Q75)

Q56. What is AKS? Azure's managed Kubernetes service. Azure manages the control plane. You manage node pools, networking choices, add-ons, and workloads.

Q57. What are node pools? Groups of VMs with the same configuration within a cluster. Use system and user pools, and separate pools for different workloads or VM families.

Q58. What networking models does AKS support? Kubenet and Azure CNI (and Azure CNI Overlay). Azure CNI gives pods VNet IPs and direct connectivity, but needs more IP planning.

Q59. How do you plan IP addresses for AKS with Azure CNI? Count nodes times max pods per node plus node IPs and reserved addresses. Size subnets for growth, and use separate subnets per node pool when needed.

Q60. What is a Kubernetes Deployment, StatefulSet, and DaemonSet? Deployment: stateless replicas with rolling updates. StatefulSet: stable identity and storage for stateful apps. DaemonSet: one pod per node, for agents like log collectors.

Q61. What is a Service and an Ingress? A Service gives stable networking to a set of pods (ClusterIP, NodePort, LoadBalancer). Ingress routes external HTTP(S) traffic to services by host and path, through an ingress controller.

Q62. What is Helm? A package manager for Kubernetes. Charts template manifests, values files set per environment, and releases are versioned and rollback-capable.

Q63. How do you manage Helm values across environments? Base values plus environment overrides, stored in Git, and deployed through the pipeline. Secrets come from Key Vault via CSI driver or external secrets, not plain values files.

Q64. What are resource requests and limits? Requests drive scheduling. Limits cap usage. Set both for predictable scheduling and to avoid noisy-neighbour problems on shared clusters.

Q65. What are liveness and readiness probes? Liveness restarts unhealthy containers. Readiness controls whether a pod gets traffic. Wrong probes can cause restart loops or outages.

Q66. How do you do zero-downtime deployments? Rolling updates with readiness probes, PodDisruptionBudgets, multiple replicas, and graceful shutdown handling.

Q67. What is a PodDisruptionBudget? A limit on how many pods of an app can be voluntarily disrupted at once, protecting availability during node upgrades or drains.

Q68. How do you handle AKS cluster upgrades? Check version support, review deprecated APIs, upgrade the control plane, then node pools one at a time with surge settings, and watch PDBs and workloads.

Q69. How do you secure an AKS cluster? Azure AD (Entra ID) integration with RBAC, private clusters or restricted API access, network policies, Azure Policy add-on, pod security standards, image scanning, and secrets from Key Vault.

Q70. What is the Key Vault CSI driver? A driver that mounts Key Vault secrets into pods, using a workload identity or managed identity, so secrets don't live in manifests.

Q71. What is workload identity in AKS? Pods get Entra ID tokens through federated credentials, so they can access Azure resources without storing secrets.

Q72. How do you monitor AKS? Container insights and Azure Monitor, Prometheus and Grafana for cluster and app metrics, and logs in Log Analytics queried with KQL.

Q73. How do you troubleshoot a pod stuck in CrashLoopBackOff? kubectl describe pod, kubectl logs --previous, check probes, resource limits (OOMKilled), config and secret mounts, then the image and entrypoint.

Q74. How do you troubleshoot a pod stuck in Pending? Check events for insufficient CPU or memory, node selectors or taints, PVC binding, and quota limits.

Q75. How do you handle autoscaling in AKS? Cluster autoscaler for nodes, and Horizontal Pod Autoscaler for pods based on CPU or custom metrics. KEDA for event-driven scaling.

F. Azure networking, security and identity (Q76–Q85)

Q76. What is a VNet, subnet, NSG? VNet is the private network. Subnets divide it. NSGs filter traffic at subnet or NIC level with allow and deny rules.

Q77. What are private endpoints and why do banks use them? A private IP in your VNet for an Azure PaaS service, so traffic stays on the private network. Usually paired with private DNS zones and public access disabled.

Q78. How does private DNS work with private endpoints? A private DNS zone linked to the VNet resolves the service name to the private IP. Missing or misconfigured links are a common cause of connectivity issues.

Q79. What is Azure Firewall vs. NSG? NSGs are layer-4 filters per subnet or NIC. Azure Firewall is a managed, centralized, stateful firewall with FQDN and threat-intel filtering. Both are often used together.

Q80. What is RBAC in Azure and how do you apply least privilege? Role assignments (role, principal, scope). Grant the smallest role at the narrowest scope, use groups, and review assignments regularly.

Q81. What is Azure Policy? Rules that enforce or audit configuration, for example allowed regions, required tags, or private endpoints only. You used policy-based automation in your work; describe that.

Q82. What is managed identity? An Entra ID identity managed by Azure for a resource, so you don't store credentials. System-assigned or user-assigned.

Q83. How do you rotate secrets? Key Vault with rotation policies or automated rotation, consumers reading the latest version, and monitoring for expired secrets.

Q84. What is the difference between Key Vault and HashiCorp Vault? Key Vault is Azure-native and integrates with Entra ID. HashiCorp Vault is multi-cloud and has dynamic secrets. You have used both; describe the use case you know best.

Q85. How do you handle a network connectivity issue between AKS and a PaaS service? Check DNS resolution from the pod, private endpoint and DNS zone links, NSG and firewall rules, route tables, and the service's firewall or public-access settings.

6. How a VM-to-AKS container migration works (template)

Important: This is a general template for how such migrations are run. Replace each step with what you actually did on the platform. Don't quote the template's numbers or steps as your own without checking.

Step 1: Discovery and inventory List every VM, its application, owner, dependencies (databases, queues, file shares, other services), OS and runtime, and its usage pattern. Identify which apps are containerizable and which should stay on VMs.

Step 2: Assessment and prioritization Score apps by effort, risk, and savings. Start with stateless or low-risk apps to build the pattern, then move the harder ones.

Step 3: Baseline the cost Record current VM spend (compute, disks, licences, backup, support time). Model the target AKS cost (node pools, right-sizing, reserved instances, shared capacity). The saving is the difference, minus new platform costs.

Step 4: Containerize Write a Dockerfile per app, move configuration out of the image into environment variables or config maps, move secrets into Key Vault, and make logs go to stdout for collection.

Step 5: Package for AKS Write Helm charts with per-environment values, define requests and limits, probes, PodDisruptionBudgets, and ingress rules. Use workload identity for Azure access.

Step 6: Networking and security Place AKS in the right subnet, set NSG rules, configure private DNS for dependencies, and align ingress with the bank's existing traffic and certificate patterns.

Step 7: Data and state Stateless apps need nothing extra. For stateful parts, decide between persistent volumes, moving data to a PaaS service, or keeping that component on a VM.

Step 8: CI/CD and environments Build a pipeline template: build, scan, push to ACR, deploy to dev, test, promote. Reuse the template for each app.

Step 9: Testing and cutover Run in parallel with the VM where possible, compare outputs, load test, then cut over with a DNS or ingress switch. Keep the VM running for a rollback window.

Step 10: Monitoring and handover Set dashboards and alerts before cutover, write runbooks, and train the application team.

Step 11: Decommission and savings tracking Stop and delete VMs only after the rollback window, remove orphaned disks and public IPs, and track actual savings against the baseline each month.

A. Kubernetes basics (1 to 20)

1. What is Kubernetes? Answer: A system that runs containers across many machines, restarts failed ones, and scales them. Simple: A manager for many small apps. It keeps them running and moves them if a machine breaks.

2. What is a container? Answer: A package with an app and its libraries. It shares the host OS kernel. Simple: A lunch box with food and a fork. Everything the meal needs is inside.

3. What is a Pod? Answer: The smallest unit in Kubernetes. One or more containers that share network and storage. Simple: A room. The containers are people sharing the room and the Wi-Fi.

4. What is a Node? Answer: A machine (VM) in the cluster that runs pods. Simple: A house. Pods are the rooms inside.

5. What is a Cluster? Answer: Control plane plus nodes, managed together. Simple: A whole apartment building, with a manager and many flats.

6. What is the control plane? Answer: The brain: API server, scheduler, controller manager, etcd. Simple: The office that decides where everything goes.

7. What is the API server? Answer: The front door. Every kubectl command and every tool talks to it. Simple: The reception desk. Everyone asks reception first.

8. What is etcd? Answer: The database that stores all cluster state. Simple: The notebook where the office writes down everything.

9. What is the scheduler? Answer: Picks which node a new pod runs on, based on free CPU, memory, and rules. Simple: A seat planner. It finds a free seat for each new person.

10. What is kubelet? Answer: An agent on each node that makes sure the containers in its pods are running. Simple: The node's supervisor, who checks each room every few seconds.

11. What is kube-proxy? Answer: Handles network rules so a Service IP reaches the right pods. Simple: A switchboard operator who connects calls to the right person.

12. What is a Namespace? Answer: A way to split one cluster into separate groups (for example, one per tenant). Simple: Folders inside one drive. Each tenant gets its own folder.

13. What are Labels and Selectors? Answer: Labels are tags on objects. Selectors find objects by tag. Simple: Stickers on boxes. A selector says "give me all boxes with a red sticker."

14. What is a ReplicaSet? Answer: Keeps a set number of identical pods running. Simple: "Always keep 3 copies of this toy on the shelf."

15. What is a Deployment? Answer: Manages ReplicaSets, rolling updates, and rollbacks. Simple: The boss of the ReplicaSet. It handles new versions and undo.

16. What is a StatefulSet? Answer: For apps that need a stable name and stable storage, like databases. Simple: Seats with name tags. Each person keeps the same seat and notebook.

17. What is a DaemonSet? Answer: Runs one pod on every node, like log collectors. Simple: One cleaner in every room.

18. What is a Job and a CronJob? Answer: A Job runs a task until it finishes. A CronJob runs a Job on a schedule. Simple: A Job is "wash the car once." A CronJob is "wash the car every Sunday."

19. What are ConfigMap and Secret? Answer: ConfigMap holds normal settings. Secret holds sensitive values (base64-encoded, not encrypted by default). Simple: ConfigMap is a notice board. Secret is a locked drawer, but the key is in the office.

20. What is kubectl? Answer: The command line tool to talk to the cluster. Simple: The remote control for the cluster.

B. Pods, probes, and YAML (21 to 40)

21. Write a simple Pod YAML. Answer:

apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
  - name: web
    image: nginx:1.25

    - containerPort: 80

Simple: Name the pod, say which image to run, and which port to open.

22. Write a Deployment YAML with 3 replicas. Answer:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.25
        ports:
        - containerPort: 80

Simple: "Keep 3 copies of this app, and here is how to make one copy."

23. Write a Service YAML. Answer:

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
  type: ClusterIP

Simple: "Give the web pods one stable address inside the cluster."

24. What are the Service types? Answer: ClusterIP (inside only), NodePort (opens a port on each node), LoadBalancer (creates a cloud load balancer). Simple: A private phone number, a door on each house, or a public shop front.

25. Write an Ingress YAML for a tenant. Answer:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tenant1
spec:
  ingressClassName: nginx
  tls:
  - hosts: [tenant1.example.com]
    secretName: tenant1-tls
  rules:
  - host: tenant1.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web
            port:
              number: 80

Simple: "When someone visits tenant1's address, send them to the web service on port 80, using this certificate."

26. What is an Ingress? Answer: Routes outside HTTP(S) traffic to services by host name and path. Simple: The gate with signs that point visitors to the right room.

27. What is an Ingress controller? Answer: The software that actually runs the gate, like NGINX or Azure Application Gateway. Simple: The gate guard. The Ingress is the list of rules he follows.

28. What is a readiness probe? Answer: Checks if a pod can take traffic. If it fails, the pod is removed from the Service. Simple: "Are you ready to play?" If no, the coach keeps you off the field.

29. What is a liveness probe? Answer: Checks if a pod is alive. If it fails, the pod is restarted. Simple: "Are you breathing?" If no, restart you.

30. What is a startup probe? Answer: Gives a slow app time to start before liveness checks begin. Simple: "Wait, the app is slow to wake up. Give it time before you check."

31. Write a probe YAML. Answer:

readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10

Simple: "Every 10 seconds, knock on /health. Start knocking after 5 seconds."

32. What are requests and limits? Answer: Requests are what a pod needs to be scheduled. Limits are the maximum it can use. Simple: Requests are the seat you book. Limits are the most food you can eat at the buffet.

33. Write a resource YAML. Answer:

resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 512Mi

Simple: "I need a quarter of a CPU and 256 MB to start. I can use up to half a CPU and 512 MB."

34. Why does a pod get OOMKilled? Answer: It used more memory than its limit, so the container is stopped. Simple: You ate more than the limit, so the waiter takes your plate.

35. What is a rolling update? Answer: Replaces old pods with new ones a few at a time, so the app stays up. Simple: Change the team players one by one, not all at once.

36. How do you roll back a Deployment? Answer: kubectl rollout undo deployment/web. Simple: Press undo to go back to the last version.

37. What is maxSurge and maxUnavailable? Answer: maxSurge is how many extra pods can be made. maxUnavailable is how many can be down at once. Simple: maxSurge is extra chairs. maxUnavailable is how many players can sit out.

38. What is a PodDisruptionBudget? Answer: Says the minimum pods that must stay running during voluntary disruption, like node drains. Simple: "At least 2 out of 3 players must stay on the field."

39. What is an HPA? Answer: Horizontal Pod Autoscaler adds or removes pods based on CPU or other metrics. Simple: More customers come, so open more checkouts.

40. What is a node selector or taint and toleration? Answer: Node selector says "run me on these nodes." Taint blocks pods from a node. Toleration lets a pod ignore that block. Simple: A sign that says "only tall people here" (taint). A tall-person badge (toleration).

41. What is a PV (Persistent Volume)? Answer: A piece of storage in the cluster, created by an admin or dynamically. Simple: A disk in the building.

42. What is a PVC (Persistent Volume Claim)? Answer: A pod's request for storage: how much and what type. Simple: "I need a 10 GB locker." The claim asks for the locker.

43. What is a StorageClass? Answer: Defines the type of storage and creates PVs on demand. Simple: A catalogue of locker types. You pick one and it's made for you.

kind: PersistentVolumeClaim
metadata:
  name: logs-pvc
spec:
  accessModes: [ReadWriteOnce]

  resources:
    requests:
      storage: 10Gi

Simple: "Give me 10 GB of disk that one pod can write to."

volumes:
- name: logs
  persistentVolumeClaim:
    claimName: logs-pvc
containers:
- name: app
  volumeMounts:
  - name: logs
    mountPath: /var/log/app

Simple: "Attach the locker to this room, at this door."

46. What is ReadWriteOnce vs ReadWriteMany? Answer: RWO: one node can write. RWX: many nodes can write (needs Azure Files or similar). Simple: RWO is one key holder. RWX is a shared folder for everyone.

47. Why do we need PVs for logs? Answer: Pods are temporary. Data on the pod disappears when it restarts, so logs go to a PV or a log service. Simple: Writing on a whiteboard that gets wiped at night. A notebook keeps it.

48. How do you get secrets into AKS? Answer: Use the Key Vault CSI driver, which mounts Key Vault secrets into the pod at start, using workload identity. Simple: The pod asks the safe for the key at the door, without storing a copy.

49. What is workload identity? Answer: The pod gets an Entra ID token with a federated credential, so it doesn't need a stored password. Simple: The pod shows an ID badge that the bank already trusts, so it doesn't need a password.

50. Why not put secrets in YAML? Answer: YAML is stored in Git and shared. Anyone with access can read it. Simple: Writing your PIN on the back of your card.

51. How are Kubernetes Secrets stored? Answer: Base64-encoded in etcd. Encrypt etcd at rest and restrict access with RBAC. Simple: A note written in code. Anyone who has the code can read it, so lock the notebook.

52. What is a ConfigMap update problem? Answer: Pods don't always reload a ConfigMap automatically. A restart or a rolling update is often needed. Simple: Changing the menu board doesn't change food already served.

53. What is a secret rotation with no downtime? Answer: Create the new secret, store it as a new Key Vault version, let new pods read it, then disable the old one after the old pods are gone. Simple: Give the new key to the new guest before taking the old key back.

54. What is kubeconfig? Answer: A file with cluster address and login details for kubectl. Simple: The address card that tells kubectl where the office is and who you are.

55. How do you connect AKS to Azure Key Vault from DevOps? Answer: Use a service connection with workload identity federation, so the pipeline gets a short token and stores no secret. Simple: The pipeline shows its badge at the vault door, and the badge expires quickly.

SCENARIO QUESTIONS (S1–S20) – fuller answers

S1. How do you know AKS has a problem? Answer: I'd check node status, pods not ready, pod restarts, and recent warning events, then confirm with alerts in Azure Monitor. In practice the first signal is usually an alert on failed pods or a node going NotReady. I'd then drill into the node or pod that's affected. Simple: The dashboard lights up red. You open the room with the red light and look at what's wrong.

S2. How does AKS report autoscaling? Answer: The cluster autoscaler writes events when it adds or removes a node, and its status is stored in a ConfigMap (cluster-autoscaler-status). I'd check those events and the status for pending pods that couldn't be scheduled. HPA shows its decisions in kubectl describe hpa. Simple: The helper writes a diary entry every time it opens or closes a room, and says why.

S3. A pod shows Pending. How do you find why? Answer: Run kubectl describe pod and read the Events section. Common reasons: insufficient CPU or memory, a node taint with no matching toleration, or a PVC that isn't bound. Then fix the cause (add capacity, fix the toleration, or fix the storage). Simple: The pod is waiting for a seat. The event log says whether there are no seats, or the seat is reserved for someone else.

S4. What is horizontal scaling? Answer: Adding more pod copies so the load is shared. In Kubernetes this is done by the HPA, based on CPU, memory, or custom metrics. It needs CPU requests set on the pods, because the percentage is calculated from requests. Simple: More cashiers when the queue grows.

S5. What is vertical scaling? Answer: Giving one pod more CPU or memory. The VPA can recommend or change requests and limits. Changing a pod's size usually restarts it, so it needs planning. Simple: Giving one cashier a bigger till, not hiring a second cashier.

S6. How does HPA decide when to scale? Answer: It compares the current average metric to the target, for example average CPU at 80% when the target is 60%. It then scales the replica count up or down, within min and max limits, with a cooldown to avoid flapping. Simple: If the team is working too hard, hire more people. If they're idle, send some home, but not every minute.

S7. Why might HPA not scale even when CPU is high? Answer: The metrics server might not be running, the pods might have no CPU requests (so the percentage can't be calculated), or the replica count may already be at the maximum. I'd check kubectl get hpa and its conditions. Simple: The scale can't measure the load, or it's already at the maximum number of workers.

S8. How do you check the cluster autoscaler is working? Answer: Look for pending pods that stay pending, check the autoscaler status and events for scale-up attempts, and check quota. If it tries to scale and fails, the reason is usually quota or the node pool's max count. Simple: Look at the waiting line. If it's long and no new rooms open, the helper is stuck, often because there's no more quota for rooms.

S9. A node is NotReady. What do you check? Answer: Check the node conditions (MemoryPressure, DiskPressure, PIDPressure), kubelet status, and the VM health in Azure. Then check if the node was being upgraded or repaired. Cordon the node if it's unstable so no new pods land on it. Simple: The house supervisor is off duty. Check if the house has power, water, and space.

S10. A pod keeps restarting. How do you find the cause? Answer: Run kubectl logs --previous to see the last run's logs, and kubectl describe pod for the exit code and last state. Exit code 137 usually means OOMKilled. Failing liveness probes also cause restarts. Simple: Read the last note the worker wrote before they fell, and check whether they were pushed (memory) or just failed their check (probe).

S11. How do you tell if a pod is out of memory? Answer: The last state shows OOMKilled, and memory usage in Container insights or Prometheus climbs up to the limit then drops. The fix is either a higher memory limit or fixing the leak in the app. Simple: The bucket overflowed, so the pod was emptied and restarted.

S12. How do you check CPU throttling? Answer: Use the container CPU throttling metric (container_cpu_cfs_throttled_periods_total in Prometheus). High throttling means the CPU limit is too low for the load, even if the node has spare CPU. Simple: The speed limit is too strict, so the car keeps slowing down even on an empty road.

S13. How do requests and limits affect scaling? Answer: HPA uses requests to calculate the percentage. Scheduling uses requests too. Limits cap what the pod can use. Setting requests too low makes HPA react strangely and can pack too many pods onto one node. Simple: The request is the price you pay to get a seat. The limit is the most you're allowed to eat.

S14. How would you scale a Databricks job cluster when it runs out of capacity? Answer: Check the instance pool and the regional VM quota first. Then move the job to another pool using the job's tag, raise the pool's max size, or request a quota increase. For urgent runs, I'd run the job in a smaller batch. Simple: The workshop is full, so move the work to another room, or ask for more space before the next shift.

S15. A tenant says their app is slow. Where do you start? Answer: Start at the front: check ingress latency and errors, then the pods' CPU, memory, and throttling, then probe failures, then dependencies like the database or Key Vault. Check for recent deployments in the same window. Tell the tenant what I've checked so far. Simple: Walk the path from the front gate to the room, and check each stop. Note the time something changed.

S16. How do you know a deployment is stuck? Answer: kubectl rollout status deployment/<name> shows it's waiting. Events show why the new pods aren't ready: failed probes, image pull errors, or a missing secret. If stuck, roll back with kubectl rollout undo. Simple: The new bus is at the stop but won't leave. The driver's note says why.

S17. How do you find which tenant uses the most CPU? Answer: Group CPU by namespace in Container insights or Prometheus. Each tenant has its own namespace, so the grouping gives per-tenant use. Pair this with node pool cost tags to explain the bill. Simple: Count the cups used in each family's kitchen, then use the same count for the bill.

S18. A pod can't reach Key Vault. What do you check? Answer: Check DNS resolution from the pod (does the vault name resolve to a private IP?), the private endpoint and its DNS zone link, the identity the pod uses, its role on the vault, and NSG rules on the subnet. Test with a debug pod to split network from permissions. Simple: Check the address, the door, and the badge, in that order.

S19. How do you prepare the platform for a peak event? Answer: Raise HPA minimum replicas and pre-scale node pools before the event, check quotas in advance, set alerts with lower thresholds, and assign someone to watch dashboards during the peak. Plan the rollback in case scale-up fails. Simple: Hire extra staff before the rush, not during it.

S20. How do you tell if a scaling change helped? Answer: Compare latency (p95 and p99), error rate, and cost for the same time window before and after the change. A change that lowers latency but doubles cost needs a decision, not just a celebration. Simple: Did the line get shorter, and did the bill go up too much?
